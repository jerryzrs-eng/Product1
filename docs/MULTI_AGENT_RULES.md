# kebiao 多 Agent 并行协作与安全队列实施规范

## 1. 目标

为 `jerryzrs-eng/kebiao` 建立可靠的多 AI Agent 协作机制，支持 Claude Code、Codex、WorkBuddy 等同时开发项目，并保证：

1. 不同 Agent 未提交的本地修改不会互相覆盖。
2. 每个并行任务拥有独立的工作目录及任务分支。
3. Agent 提交和推送前进行安全检查。
4. 多个 Agent 准备合并 `master` 时，自动排队、依次验证并合并。
5. 多个 Agent 准备发布 Release 时，自动排队，避免版本、标签及附件竞争。
6. 发生冲突时优先规避或等待，不使用破坏性的 Git 命令。
7. Agent 异常退出、CI 失败或任务超时后，系统不会永久锁死。
8. 所有修改和发布均保留真实、可验证的溯源记录。
9. 尽可能自动运行，不要求用户日常手动管理任务队列。
10. 不破坏项目现有的构建、测试、安装包及发布流程。

本项目的设计原则是：

**开发并行、共享资源串行、操作可恢复、记录可追溯。**

## 2. 实施前检查

Codex 必须首先检查当前仓库，而不是直接按照假定的结构修改。

重点检查：

- `AGENTS.md`
- `CLAUDE.md`
- `.github/workflows/build.yml`
- 现有分支与 Worktree
- GitHub Actions 权限
- GitHub 分支保护或 Rulesets
- Release 发布方式
- 更新说明及 Agent 署名规则
- 已有自动化脚本和 Git hooks
- 当前工作目录中的未提交修改
- 现有 CI 与发布状态

必须复用已经存在且正常工作的功能，避免重复开发。

不得覆盖尚未提交的修改，不得破坏现有版本标签，不得擅自重新发布历史版本。

## 3. 多 Agent 工作目录隔离

### 3.1 基本结构

推荐使用 Git Worktree：

```
项目工作区/
│
├── kebiao/                  # 主工作目录，master
│
├── kebiao-claude/           # Claude Code 工作目录
│
├── kebiao-codex/            # Codex 工作目录
│
└── kebiao-workbuddy/        # WorkBuddy 工作目录
```

对应分支示例：

```
master
agent/claude-task
agent/codex-task
agent/workbuddy-task
```

各工作目录是并列关系，并非互相嵌套，也不是独立 Git 仓库。

所有 Worktree 共享同一仓库的历史和 Git 对象数据库，但工作区、暂存区与检出状态相互独立。

### 3.2 任务隔离

实际使用时优先采用每个并行任务一个 Worktree，而不是永久为每种 Agent 固定一个目录。

例如：

```
kebiao-claude-layout/
kebiao-claude-import/
kebiao-codex-tests/
kebiao-workbuddy-settings/
```

各任务必须拥有独立分支，不得让多个同时写入的 Agent 共用同一工作目录。

### 3.3 实施要求

实现安全的本地辅助命令或脚本，用于：

- 查看现有 Worktree。
- 创建任务分支和 Worktree。
- 检查目录或分支是否已存在。
- 显示任务对应的 Agent、分支及目录。
- 安全清理已完成的任务工作目录。

创建时不得覆盖已有目录。

清理时必须检查未提交修改、未推送提交和任务状态，不得强制删除仍在使用的目录。

任何自动化脚本不得假设所有 Agent 都在同一台计算机运行。

## 4. 修改、提交和推送保护

### 4.1 修改前

Agent 必须：

1. 确认当前工作目录及分支。
2. 执行 `git status`。
3. 获取远程最新提交信息。
4. 检查本地 Worktree 和已知开放 PR。
5. 识别可能与其他任务重叠的文件或功能。

如果其他任务正在修改相同文件，应尽可能先处理独立任务。

工作目录隔离不能代替业务逻辑冲突检查。

### 4.2 提交前

Agent 必须：

1. 检查所有待提交文件。
2. 核实修改确实属于本次任务。
3. 避免将其他任务的代码混入提交。
4. 运行必要测试。
5. 按现有第 7 节 Agent 署名规则记录真实身份。
6. 不得擅自删除、覆盖、重置其他任务的修改。

优先显式指定提交文件或使用交互式暂存。

不得无条件使用 `git add -A` 提交整个共享工作区。

### 4.3 推送前

必须检查远程分支是否变化。

如果远程分支已经发生变化：

1. 获取最新提交。
2. 检查本地和远程差异。
3. 安全合并或变基。
4. 重新运行受影响的测试。
5. 验证后再推送。

禁止通过 `git push --force`、未经确认的 `git reset --hard` 或删除他人提交来解决冲突。

Git 拒绝推送时，应报告并处理原因，而不是强行覆盖。

## 5. Agent 协作任务状态

建立统一的任务状态约定：

| 状态           | 含义        |
| ------------ | --------- |
| `developing` | 正在独立开发    |
| `ready`      | 开发完成，等待检查 |
| `queued`     | 已进入关键操作队列 |
| `running`    | 正在执行合并或发布 |
| `blocked`    | 检查失败或需要协调 |
| `completed`  | 操作成功完成    |
| `failed`     | 操作失败      |
| `cancelled`  | 任务已取消     |

需要记录：

- 任务标识
- Agent 名称
- Agent 模型（如可确认）
- 工作目录或任务分支
- 目标操作
- 对应 PR 或版本
- 关联 Commit SHA
- 当前状态
- 创建及更新时间
- GitHub Actions Run 链接（如适用）

状态必须来自真实 Git、PR、Workflow 或协调系统数据。

不得仅因某个 Agent 声称任务完成，就认定 GitHub 操作已经成功。

不应通过一个所有 Agent 同时修改的普通 JSON 文件实现并发队列；若使用文件存储，需要证明更新具有可靠的原子性和冲突恢复机制。

## 6. master 自动合并队列

### 6.1 目标

多个 Agent 同时提交 PR 时，允许排队并依次安全合并进入 `master`。

队列名称建议：

`kebiao-master-merge`

### 6.2 实现方式

由于当前仓库属于 GitHub 个人账号，优先采用 GitHub Actions 实现轻量级合并协调流程。

要求：

1. 所有 Agent 通过独立分支和 PR 提交修改。
2. PR 首先运行必要的 CI。
3. 满足条件的 PR 可以进入合并请求队列。
4. 合并操作必须由统一协调流程串行执行。
5. 每次合并前重新获取最新 `master`。
6. 验证 PR 仍然开放、允许合并、目标正确且未被替换。
7. 验证候选代码与最新主分支的合并结果。
8. 重新确认必需检查通过后再执行合并。
9. 合并成功后记录实际 Merge Commit SHA。
10. 释放执行资格，继续处理其他请求。

可以使用 Actions 的并发控制作为串行执行基础，但必须确保实际合并操作都经过同一协调入口。

不能仅增加 `concurrency` 就声称 PR 已具备自动合并队列。

### 6.3 竞争状态处理

必须处理以下情况：

- 两个 Agent 同时请求合并。
- 等待期间 `master` 已被更新。
- PR 在排队后追加了新的提交。
- PR 在排队期间被关闭。
- PR 已经被其他执行者合并。
- 原本通过的 CI 因代码变化而过期。
- 自动合并时遇到语义或文本冲突。
- Actions 失败、取消或超时。

执行合并前必须校验预期 PR Head SHA，避免合并未经审核的新提交。

不得基于陈旧的合并检查结果继续操作。

### 6.4 冲突处理

当合并失败时：

- 可安全重试的临时错误允许有限次数重试。
- CI 失败应标记为 `blocked`。
- 无法安全解决的代码冲突应标记为 `blocked`。
- 不得自动选择一方代码覆盖另一方。
- 一个任务被阻塞，不应永久阻塞后续独立且安全的任务。
- 记录明确的阻塞原因和需要处理的操作。

### 6.5 安全要求

优先通过 GitHub 分支保护和最小权限机制约束主分支写入。

不能在普通 PR 工作流中直接执行不受保护的主分支写入。

必须考虑来自 PR 的不可信代码，不得让其任意获取具有主分支写入权限的 Token。

如果当前 GitHub 权限不支持可靠的自动合并，应实现安全的 PR 检查及人工确认模式，而不是绕过保护规则。

## 7. Release 自动发布队列

### 7.1 目标

同一时间只允许一个正式发布操作修改 Release、版本标签及发布附件。

队列名称建议：

`kebiao-release`

### 7.2 实现方式

优先将正式发布步骤从普通 CI 中逻辑隔离或拆分为独立工作流，避免非发布任务占用发布队列。

在当前 GitHub Actions 支持的情况下，使用：

```
concurrency:
  group: kebiao-release
  cancel-in-progress: false
  queue: max
```

要求：

- 同组最多一个发布任务运行。
- 等待任务不应被后续任务默认替换。
- 队列超额、超时或取消必须有明确处理。
- 排队期间不得修改共享 Release 资源。
- 正常开发及普通测试不应无故阻塞。

实际配置必须经过工作流语法验证。

### 7.3 发布前检查

获得执行资格后，必须重新验证：

1. 版本号合法。
2. 版本标签与目标提交一致。
3. 更新说明存在。
4. Agent 署名符合当前约束。
5. 必需 CI 已通过。
6. 安装包来自指定提交。
7. 没有发生不允许的标签覆盖。
8. 不会误修改其他版本的 Release。

发布执行时应保存完整的操作结果和对应 Run URL。

### 7.4 已存在的 Release

必须区分：

- 创建新的正式 Release。
- 对已有 Release 进行明确授权的修复或附件替换。
- 重复触发同一发布任务。

默认禁止静默覆盖已发布的版本。

如果版本已存在，不得直接删除原有安装包再尝试上传新安装包。

需要实现安全的重复执行与失败恢复策略。

对于无法保证原子性的多步操作，应明确记录风险，并避免执行可能导致历史版本附件丢失的自动替换。

### 7.5 发布后验证

发布后必须：

1. 验证 Release 存在。
2. 确认 Tag 指向正确的 SHA。
3. 验证安装包存在。
4. 下载发布附件并核对 SHA256。
5. 记录 Agent 身份、版本、Commit SHA、Run URL。
6. 只有全部检查通过后才能报告成功。

发布失败时应保留已存在且有效的版本资料。

## 8. Agent 身份与操作溯源

必须兼容现有 `AGENTS.md` 第 7 节及历史发布说明。

建议记录并区分：

- 开发 Agent
- 提交 Agent
- 发布 Agent
- 开发模型
- 关联 Commit SHA
- 关联 PR
- 发布 Tag
- GitHub Actions Run
- Agent 会话链接（如可提供）

必须如实填写。

无法确认的内容统一填写「未确认」或「未提供」。

不要把 GitHub 提交账号等同于实际使用的 AI 模型。

不要因缺少可分享的 Agent 会话而编造链接。

CI 可以验证记录格式与关联对象是否存在，但不能仅凭文本证明真实 AI 身份。

## 9. 任务排队、等待与异常恢复

### 9.1 等待原则

其他 Agent 占用关键资源时，新任务应进入真实的等待队列。

等待中的 Agent 可以继续进行安全的独立开发，但不得同时修改被占用的共享资源。

禁止无限循环查询 GitHub 状态。

优先让后台协调服务或 GitHub Actions 管理等待任务。

### 9.2 异常场景

必须考虑：

- 执行中的 Agent 意外退出。
- 工作流运行失败或取消。
- GitHub API 临时不可用。
- 权限不足。
- PR 检查结果过期。
- 发布队列长时间无进展。
- 同一个请求重复入队。
- 多个任务互相等待。

所有等待任务必须有明确状态、超时或失败处理。

不能把任意时长的等待视为成功。

### 9.3 防止永久锁定

不得依赖 Agent 自己维护的永久锁文件作为唯一协调机制。

优先利用 GitHub Actions 的运行生命周期释放执行资格。

如果确实需要自定义任务锁，必须实现：

- 锁所有者记录
- 唯一任务标识
- 租约有效期
- 心跳或续租
- 异常恢复
- 幂等重试
- 安全释放
- 防止旧执行者继续写入的机制

在没有充分必要性的情况下，不引入复杂的自定义分布式锁服务。

## 10. CI 与 GitHub 权限

检查现有工作流是否支持：

- `push`
- `pull_request`
- 手动发布
- Tag 发布
- 必需状态检查
- 受控写入权限

普通 PR 测试应尽可能采用只读权限。

有权限修改 `master` 或 Release 的步骤必须限制执行来源和触发条件。

不得为了实现队列而默认给所有 PR 代码开放写入权限。

现有构建功能必须保留，包括：

- .NET 单元测试
- Windows 程序构建
- 界面截图
- 模板生成
- 安装包制作
- 静默安装及卸载验证
- 构建产物上传
- Release 下载和 SHA256 检查

必须避免 GitHub 分支保护规则与 CI 互相依赖，导致仓库无法合并任何 PR。

## 11. AGENTS.md 更新

保留现有第 1～7 节协作要求，不得无故删除或重写。

整理第 8 节「多 Agent 并行开发与冲突保护」，覆盖：

1. Worktree 隔离
2. 工作目录示例
3. 修改前检查
4. 提交前检查
5. 推送前检查
6. 冲突自动规避
7. 主分支保护
8. Release 串行发布
9. Worktree 清理
10. 自动化能力边界
11. 关键操作排队与自动等待

必须明确说明：

- 哪些能力已经通过脚本或 CI 实现。
- 哪些属于 Agent 行为约定。
- 哪些需要 GitHub 仓库管理员启用。
- 哪些由于平台权限限制暂时无法实现。

不得把尚未实现的保护机制描述为已经生效。

## 12. 推荐实施阶段

### 阶段一：安全开发基础

- 审计当前仓库。
- 整理 `AGENTS.md`。
- 实现 Worktree 辅助脚本。
- 实现提交和推送安全检查。
- 为 PR 建立独立 CI。
- 验证现有构建流程不受影响。

### 阶段二：串行发布

- 隔离正式发布任务。
- 建立 Release 队列。
- 增加发布前版本及 SHA 检查。
- 处理重复发布和异常退出。
- 保留安装包完整性验证。

### 阶段三：master 合并协调

- 实现统一 PR 合并请求入口。
- 建立串行合并机制。
- 在执行时重新验证 PR、最新 `master` 和 CI。
- 增加失败隔离及恢复机制。
- 配合实际权限实施分支保护。

### 阶段四：溯源与验收

- 统一 Agent 署名字段。
- 关联 PR、Commit、Release 和 Actions Run。
- 测试多 Agent 同时提交和发布。
- 输出使用说明及最终验收报告。

优先采用最简单、可验证、可维护的实现。

不得为实现表面上的完全自动化而牺牲安全性。

## 13. 验收测试

至少验证以下场景：

| 编号  | 测试场景                         | 预期结果             |
| --- | ---------------------------- | ---------------- |
| T01 | 两个 Agent 同时修改不同文件            | 独立开发成功           |
| T02 | 两个 Agent 在不同 Worktree 修改同名文件 | 未提交文件互不覆盖        |
| T03 | 两个 Agent 同时提交自己的分支           | 各自提交成功           |
| T04 | 两个 Agent 同时请求合并 master       | 依次执行，不丢失提交       |
| T05 | 第一个合并后第二个 PR 已过期             | 重新检查最新主分支        |
| T06 | 合并存在代码冲突                     | 标记阻塞，不强制覆盖       |
| T07 | 一个 PR 合并失败                   | 不永久阻塞其他安全任务      |
| T08 | 两个 Agent 同时请求发布              | 发布操作串行执行         |
| T09 | 重复请求同一版本发布                   | 不静默删除或覆盖已有附件     |
| T10 | 运行中的工作流失败或取消                 | 状态明确，可恢复         |
| T11 | 任务 Worktree 有未提交文件           | 拒绝危险清理           |
| T12 | 提交包含 Agent 署名                | 能追踪已声明的 Agent    |
| T13 | Release 对应的安装包与 SHA256 不一致   | 发布检查失败           |
| T14 | 普通 PR 包含不可信代码                | 不能借 CI 取得主分支写入权限 |

测试应尽可能使用临时分支、模拟操作及测试版本。

不得为了验收而修改、覆盖或删除已有正式 Release。

## 14. 最终交付

Codex 完成后应提供：

1. 实际修改的文件清单。
2. 每个新增脚本和 Workflow 的用途。
3. `AGENTS.md` 的最终规则。
4. Worktree 创建、查看和安全清理的使用方法。
5. PR 合并队列的实际使用方法。
6. Release 排队发布的方法。
7. 已执行的测试及结果。
8. 哪些机制已经自动生效。
9. 哪些 GitHub 权限或保护规则需要用户手动设置。
10. 尚未解决的限制和风险。
11. 修改对应的 Commit SHA 和 PR 链接（如有）。

不得使用没有验证过的「已完成」「已生效」「全自动」等结论。

## 15. 禁止事项

实施期间不得：

- 删除现有项目历史。
- 强制推送覆盖共享分支。
- 擅自覆盖其他 Agent 的工作目录。
- 擅自删除现有 Release 或 Tag。
- 为测试而重复发布正式历史版本。
- 未经确认修改 GitHub 仓库所有权。
- 为获得原生 Merge Queue 而擅自迁移仓库。
- 随意扩大 GitHub Token 权限。
- 破坏现有安装包构建及发布能力。
- 自动启用未经验证、可能锁死主分支的保护规则。
- 将仅存在于文档中的机制称为已经实现。

## 16. 完成标准

最终应该达到：

- 多 Agent 可以并行开发。
- 未提交修改在不同工作目录之间互不覆盖。
- 各 Agent 可以独立提交任务分支。
- 合并 `master` 有明确且安全的串行协调机制。
- 发布 Release 有真实队列和异常处理机制。
- 失败任务不会永久阻塞其他任务。
- 核心操作具有可查的提交和运行证据。
- 原有 CI、构建和安装包发布能力保持正常。
- 不依赖用户频繁手动协调日常并行开发。

若 GitHub 权限、平台能力或当前执行环境限制了某项功能，必须如实说明并采取安全的降级方案，不得假装实现。

## 17. 正式发布授权（优先适用）

开发任务可以按已启用的机制创建 PR、运行 CI 并合并 `master`。正式 Release 必须由仓库所有者明确授权并在 GitHub 审批。普通推送、PR 合并、CI 成功和推送版本标签都不能触发正式发布。

1. Agent 从 `master` 手动发起发布请求，填写版本和获授权的完整 Commit SHA。记录 Actions Run 链接，让所有者核对版本、SHA 和测试结果。
2. 仓库所有者亲自在 `kebiao-release` 环境审批。Agent 使用不同的、已有授权的 GitHub 身份发起请求。流程检查环境中唯一审批者为仓库所有者、禁止自审，并在写入 Release 前查询本次运行的实际审批记录。
3. 构建和发布两次检出均固定为输入的 SHA，并验证它属于最新 `master` 的历史。审批校验脚本来自发起工作流时的 `master` 提交。队列等待期间继续使用授权 SHA。失败或取消后，用新运行重新请求审批。
4. 维护者需要创建 `kebiao-release` 环境，设置仓库所有者为唯一必需审批者、开启禁止自审、关闭管理员绕过审批并将部署分支限定为 `master`。环境或审批记录缺失时工作流停止。审批等待超过 GitHub 平台期限会失败，取消过时请求可释放队列位置。
5. 仓库侧还需限制绕过工作流的共享写权限。拥有可直接管理 Release 的账号或令牌仍可从工作流外操作。保护工作流变更、限制发布标签和直写权限需要维护者配置。若所有 Agent 与用户共用同一 GitHub 身份，禁止自审会阻止该流程，待维护者选定现有且独立的授权身份后再启用。
6. 测试使用临时仓库、模拟 API 或普通 CI。不得通过测试创建正式 Release、改动历史 Release、扩大发起者凭证权限或变更仓库所有权。

切换前，现有 `master` 仍含旧的 Tag 发布入口。合并后，向带旧工作流的历史提交新打标签也可能运行旧逻辑。维护者应限制 `v*` 标签的创建、更新和删除，并核对只有受控发布身份拥有所需权限。环境审批只约束引用该环境的作业，历史工作流和可直接创建 Release 的身份必须另行约束。

## 18. 当前实现与启用方式

第 1～16 节是完整实施规范。第 17 节是后续确认的发布授权规则，优先于前文。本节记录本分支的实施范围。

### 工作目录与提交

在同一克隆中每个任务使用一个相邻的 Worktree。运行以下命令前，先读本规范并检查 `git status`、远端分支和相关开放 PR。

```powershell
pwsh -File scripts/AgentWorktree.ps1 -Action List
pwsh -File scripts/AgentWorktree.ps1 -Action New -Agent codex -Task import
# 在新建的任务目录内
pwsh -File scripts/AgentWorktree.ps1 -Action Check
git config --local core.hooksPath .githooks
git push -u origin agent/codex-import
# 任务合并后，从仍保留的主工作目录执行
pwsh -File scripts/AgentWorktree.ps1 -Action Remove -Agent codex -Task import -Completed
```

每台机器需自行启用 hooks。先检查 `git config --show-origin --get core.hooksPath`，已有 hooks 时由维护者整合。设置对当前克隆及其 Worktree 生效。清理要求工作目录干净，且当前提交已进入最新远端 `master`。Git 执行非强制移除并保留分支。hooks 检查任务 Worktree、暂存差异、提交署名、推送目标及快进关系。连接器/API 和未启用 hooks 的机器由服务器规则及 CI 约束。文件重叠仍需检查开放 PR 和协调工作范围。

### PR 和合并协调

`build.yml` 对目标为 `master` 的 PR 单独运行只读的 **Windows 构建** 检查，同时支持 `merge_group`。Agent 分支的非合并提交必须有第 7 节署名。PR 测试使用 GitHub 的合并检出，并运行完整 Windows 构建、截图、安装包制作和安装实测。写入 Release 和截图分支的作业只接受指定的推送或手动事件。

`master 合并协调` 工作流通过 Actions 手动发起。输入已审核的 PR 编号和完整 Head SHA。每次请求在 `kebiao-master-merge` 组串行执行。获得执行资格后，工作流重新获取最新 `master` 和 PR Head，要求任务分支包含最新主分支，并核对同一 PR Head 的最新 PR 构建。合并 API 再以 Head SHA 限定目标。合并提交和验证运行写入摘要。关闭、草稿、冲突、过期、未通过检查和已合并的请求会退出。更新分支后用新的 Head SHA 重新入队。

**尚未启用。** 先将工作流合并到 `master`。维护者在 GitHub 为 `master` 启用 Ruleset，要求通过 PR、启用严格的 **Windows 构建** 必需检查（来源选 GitHub Actions）、阻止强推和删除，并保证合并执行身份受这些规则约束。再确认允许 merge commit，最后设置 Actions 仓库变量 `KEBIAO_ENABLE_MERGE_COORDINATOR=true`。保护规则缺失时协调器拒绝合并。在此之前由维护者核对最新提交和 PR CI 后逐个合并。GitHub 原生 Merge Queue 和独立任务状态服务尚未启用。任务状态从 PR、Git 和 Actions 读取。

### Release 队列与恢复

使用 `构建` 工作流从 `master` 手动提交版本号和授权 SHA，按第 17 节完成 GitHub 环境审批。普通构建可并行，只有 **正式发布** 作业进入 `kebiao-release`。发布作业取得执行资格后再次核对来源、版本、署名、提交范围与真实审批记录，从同一次运行下载安装包，校验草稿附件后公开，再下载正式附件校验 SHA-256。

两个队列用 GitHub Actions 的 `queue: max` 等待模式，最多各排队 100 项。合并执行限时 5 分钟，发布执行限时 15 分钟，失败或取消后 GitHub 释放执行资格。检查具体 Run 的状态和日志再有限重试。发布遇到同名草稿或正式 Release 时停止。公开草稿前，如果同名 Tag 已存在，必须指向授权 SHA。如果 Tag 尚不存在，通过 GitHub API 按该 SHA 创建。失败留下的草稿和 Tag 由维护者核对来源与附件，再决定如何恢复。已公开版本的附件修复是单独授权的操作。

发布和合并保护约束的是这些工作流入口。维护者还需在仓库侧限制可修改共享分支、标签和发布记录的身份，并审核工作流、hooks 和规则文件的变更。CI 结果可证明检查执行及通过，Agent 是否实际阅读规范和署名是否真实由参与者如实记录。
